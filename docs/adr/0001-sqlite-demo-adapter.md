# ADR-0001: SQLite как переносимый адаптер DEMO

Статус: принято для локального P0-DEMO 2026-10-25.

## Контекст

Целевой стек проекта использует PostgreSQL, но на машине разработки отсутствуют Docker и `psql`. Пользователь явно разрешил переносимый SQLite fallback, если ограничение будет обозначено честно и не изменит целевую архитектуру.

## Решение

Локальный demo по умолчанию хранит все записи в `data/demo.db`. SQLAlchemy и Alembic остаются границей доступа и миграций. Seed выполняется только для пустой БД и никогда не очищает её при старте. Reset возможен только явной командой `python -m app.seed --reset`. Backup/restore выполняется `python -m app.backup`.

Модель содержит ограничения, необходимые и для SQLite, и для PostgreSQL: внешние ключи, уникальность idempotency/semantic completion, partial unique для единственной активной genealogy-привязки, уникальные quality audit и calculation snapshot.

## Последствия и ограничения

- Это не подтверждение production-совместимости PostgreSQL: Compose и миграции PostgreSQL должны быть проверены в окружении с движком.
- SQLite не моделирует конкурентность, блокировки, типы и эксплуатационные характеристики PostgreSQL полностью.
- Локальные тесты подтверждают функциональную семантику доступного адаптера, но не заменяют concurrency/load/backup-restore испытания целевой БД.
- Перед реальным пилотом обязательны PostgreSQL migration rehearsal, конкурентные тесты attach/scan/approval, `pg_dump/pg_restore`, мониторинг и runbook восстановления.
