# Демо-сценарии P0

Статус: детерминированный синтетический набор для разработки и портфолио. Все идентификаторы, нормы, часы, дефекты и результаты ниже имеют префикс/маркировку `ДЕМО` и не являются данными или нормативами завода.

## 1. Назначение

Базовый seed одним воспроизводимым запуском показывает:

- пять рядов и явные сменные назначения сотрудников;
- настраиваемый маршрут одной пилотной модели;
- `component → WIP → final serial` и замену компонента;
- принятые primary-события, готовое изделие и незавершённые WIP;
- производственный KPI и отдельный KPI ОТК;
- независимый аудит решений ОТК.

Rework, идемпотентный retry, конфликт изменённого payload, semantic duplicate, route violation, отсутствие аудита и неполная когорта создаются API-тестами либо интерактивным сценарием поверх базового seed. Они не объявляются предзаполненными фактами. Missing norm, biased audit, scrap и pending scan покрыты расчётными/контрактными требованиями, но в compact seed не засеяны.

Генератор не использует случайность. Идентификаторы, UTC-время и порядок событий фиксированы, поэтому повторный seed создаёт тот же результат или идемпотентно сообщает, что набор уже существует.

## 2. Площадка, смена и пять рядов

Площадка: `DEMO-PLANT-01`. Часовой пояс: `Europe/Moscow`. Смена `DEMO-SHIFT-2026-10-25-D`: 08:00–16:00 локального времени.

| Ряд | Назначение в демо | Важное ограничение |
|---|---|---|
| `DEMO-SOLDER-01` | Синтетическая операция пайки узла управления | Физический процесс не считается моделью реального завода |
| `DEMO-ASM-01` | Альтернативный сборочный ряд | Не является обязательным предшественником ASM-02/03 |
| `DEMO-ASM-02` | Альтернативный сборочный ряд | Изделие выбирает один сборочный ряд |
| `DEMO-ASM-03` | Альтернативный сборочный ряд | Изделие выбирает один сборочный ряд |
| `DEMO-QC-01` | Первичный контроль ОТК | Решение ОТК и независимый аудит — разные события и роли |

Маршрут `DEMO-ROUTE-Q1-V1`:

```text
DEMO-SOLDER-CONTROLLER
  → ровно одна из DEMO-ASSEMBLE@ASM-01/02/03
  → DEMO-QC-FIRST-PASS
  → DEMO-FINAL-LINK при положительном исходе
```

Три сборочных ряда — альтернативные производственные полосы в этом **демо-маршруте**. Это не утверждение о реальном маршруте завода.

## 3. Синтетические нормы и план

Версия норм: `DEMO-NORM-V1`; версия плана: `DEMO-PLAN-V1`; `rho_target=1.00 НЧ/чел.-ч`; `Q_min=0.60`. Значения выбраны только для наглядности тестов.

| Операция | Норма, человеко-минут |
|---|---:|
| `DEMO-SOLDER-CONTROLLER` | 6 |
| `DEMO-ASSEMBLE` | 12 |
| `DEMO-QC-FIRST-PASS` | 4 |
| `DEMO-FINAL-LINK` | 1 |

Плановые строки фиксируются по смене, модели, route step и, для сборки, ряду. Сверхплан одного ряда не покрывает дефицит другого без явного правила версии плана.

Для golden-тестов расчётного ядра используются отдельные синтетические позиции A/B из `docs/01-product-and-metrics.md`; они не добавляют вторую производственную модель в основной seed.

## 4. Назначения и человеко-часы

| Учётная запись | Интервал | Назначение |
|---|---|---|
| `solder` | 08:00–16:00 | SOLDER-01, primary TIME_ENTRY |
| `assembly1` | 08:00–16:00 | ASM-01, primary TIME_ENTRY |
| `assembly2` | 08:00–16:00 | ASM-02, primary TIME_ENTRY |
| `assembly3` | 08:00–16:00 | ASM-03, primary TIME_ENTRY |
| `qc` | 08:00–16:00 | QC-01, primary TIME_ENTRY и исходные решения |
| `foreman` | 08:00–16:00 | ASM-01, support TIME_ENTRY |
| `auditor` | — | Независимый аудит решений ОТК; в baseline нет производственного TIME_ENTRY |

Compact seed содержит одного демонстрационного бригадира; требование назначения бригадира каждому ряду остаётся частью целевой модели, а не выдуманным фактом seed. `H_accounted` строится только из синтетического TIME_ENTRY ledger; интервалы между сканами его не меняют. Baseline даёт `H_accounted=40 чел.-ч` для производства (пайка, три ряда сборки и support бригадира) и `8 чел.-ч` для ОТК. API-тест отдельно подтверждает: rework-часы пайки/сборки потребляют ресурс, но не создают второй earned output; часы ОТК не попадают в производственный rework-контур. Изменение состава/перевод сотрудника поддерживаются моделью назначений, но не засеяны как отдельный baseline-факт.

## 5. Экземпляры и события

Сериализованные компоненты имеют идентификаторы `DEMO-COMP-*`, WIP — `DEMO-WIP-*`, готовые изделия — `DEMO-FINAL-*`.

| Сценарий | Детерминированный результат |
|---|---|
| `DEMO-WIP-001` | Пайка → ASM-01 → первичный ОТК accept; связан с `DEMO-FINAL-001` |
| `DEMO-WIP-002` | Пайка → ASM-02 → первичный ОТК reject; остаётся WIP в baseline |
| `DEMO-WIP-003` | Пайка → ASM-03 → первичный ОТК accept; компонент `DEMO-COMP-MOTOR-003A` заменён на `...003B`, обе связи остаются в истории |
| `DEMO-WIP-004..008` | Созданы как незавершённые WIP без operation events; final serial не присвоен |

Исправления — только связанными компенсирующими событиями. Component, WIP и final никогда не суммируются как один тип выпуска.

Негативные сценарии не маскируются под seed-данные: `tests/test_api_metrics_contract.py` создаёт retry/конфликт UUID/semantic duplicate/чужое назначение/rework/no-audit, а `tests/test_calculation_services.py` — новую версию плана, correction, unplanned primary, неполную когорту, superseded TIME_ENTRY и проверку закреплённой версии норм.

## 6. ОТК и независимый аудит

Compact seed создаёт три первичных решения ОТК для `DEMO-WIP-001..003` (два accept, один reject) и три независимых audit events другой ролью. Все три решения подтверждены аудитором как корректные. Подтверждённый reject — результат контроля и не штрафует контролёра.

Фактический baseline, пересчитанный из БД:

| Контур | E_plan, НЧ | E_fact, НЧ | E_plan_covered, НЧ | H_accounted, чел.-ч | Q | KPI_raw |
|---|---:|---:|---:|---:|---:|---:|
| Производство (пайка + сборка) | 1,8 | 0,9 | 0,9 | 40 | 2/3 | 1,5% |
| ОТК | 0,4 | 0,2 | 0,2 | 8 | 3/3 | 2,5% |

Низкие демонстрационные значения производительности вызваны намеренно компактным числом operation events при полной восьмичасовой смене. Seed не подгоняется под красивый KPI. Для производства `A_volume=A_plan=0,5`, `P=0,0225`; для ОТК `A_volume=A_plan=0,5`, `P=0,025`, `Q_decision=1`. `timeliness=NULL`, потому что SLA срока решения в demo-методике не задан.

Все количества получаются агрегацией сохранённых `OperationEvent`, решений ОТК, независимых audit events и TIME_ENTRY. Seed не записывает изготовленные заранее cached metrics вместо первичных событий; проекции и расчёт должны быть пересобираемы из журнала.

Два отрицательных контрольных сценария проверяются расчётными/API-тестами, а не хранятся как baseline-записи:

1. `DEMO-AUDIT-NONE`: независимых решений нет — `Q_decision=NULL`, не 100%;
2. `DEMO-AUDIT-BIASED`: выборка заведомо смещена и не имеет утверждённых весов — `Q_decision=NULL`, composite ОТК `NULL`.

Найденный контролёром подтверждённый производственный дефект относится к входящему качеству, а не штрафует контролёра. Ложное отклонение относится к качеству решения ОТК.

## 7. Golden-результаты расчётного ядра

| Проверка | Ожидается |
|---|---|
| План A=100×6 мин, B=50×12 мин; факт A=90, B=55 | `A_volume=100%`, `A_plan=95%`, `Q=95%`, `KPI_raw=90,25%` |
| `E_plan=20`, `E_fact=18`, covered=18, `H=15`, `Q=97%` | `P=120%`, `KPI_raw=87,3%` |
| 100 primary×6 мин, `H_accounted=12`, включая rework=2 | `E_fact=10 НЧ`, `P=83,33%`, rework share=16,67% |
| Валидный независимый аудит ОТК 96/100 в unit-golden case | `KPI_otk_raw=86,4%`; это не KPI compact seed |
| Когорты 9/10 и 90/90 | Сводный `Q=99%`, не 95% |
| Нет выпуска при положительном плане | `A_volume=0`, `A_plan=0`, `P=0` при положительных часах; `Q/KPI=NULL` |
| Нет плана, нормы, часов, зрелой базы или валидного аудита | Зависимый показатель `NULL` и стабильный reason code |

Расчёт возвращает неокруглённые `Decimal`. Округление `ROUND_HALF_UP` применяется только для представления. В API Decimal сериализуется канонической десятичной строкой, `None` — JSON `null`, причины — массивом строк.

## 8. Проверки доступа и устойчивости

- работник не может подменить `assignment_id` на чужой — ожидается 403;
- повтор UUID с изменённым body — 409, а не идемпотентный успех;
- новый UUID для уже закрытой primary operation — semantic duplicate без роста `E_fact`;
- retry исходного UUID не меняет автора после reload/re-auth;
- контролёр не аудирует своё решение;
- закрытие смены не превращает незрелый KPI в `FINAL`;
- API-тесты используют временный SQLite-файл и не меняют демонстрационную БД.

Исполняемые проверки находятся в `tests/test_metrics.py`, `tests/test_calculation_services.py`, `tests/test_api_metrics_contract.py` и `tests/test_api_workflows.py`.
