# Постоянный контекст: UX / frontend / QA / инфографика

## Роль

Отвечаю за пользовательские сценарии, frontend React/TypeScript, доступность, понятность методики, RBAC, приёмочные критерии, портфолио-демо и инфографику. Demo MVP реализован и работает только с живым API; расчёт KPI остаётся authoritative на backend.

## Контекст продукта

- Реальное производство квадрокоптеров; многопользовательский веб-инструмент.
- Пять рядов: три сборки, один пайки, один ОТК; на каждом бригадир.
- Состав меняется ежедневно; у каждого работника отдельный компьютер/планшет со сканером.
- Детали имеют QR, узлы/WIP — предлагаемый для согласования временный код, готовый квадрокоптер — финальный QR/серийный идентификатор; маршрут настраиваемый.
- Три участка KPI: сборка, пайка, ОТК.
- Компоненты: «Выполнение номенклатурного плана (A_plan) · Качество с первого предъявления (Q) · Производительность труда (P)»; отдельно показывается «Валовый объём (A_volume)». `A_plan=Σ[min(qfact_i,qplan_i)×s_i]/E_plan`, `КПД=100×min(A_plan,P,1)×Q`; нормы задаёт завод.
- Портфолио показывает автоматизацию только на явно синтетических данных.

## Принятые решения

1. Скан привязывается к работнику, устройству, месту, операции, смене и версии маршрута.
2. Межскановый интервал не считается чистым трудовым временем автоматически.
3. Дубли, нарушения маршрута и переделки — явные типы/связанные события, а не удаляемые ошибки. Genealogy MVP: serial attach/detach/replace, WIP→final link, scrap/rework; партийные split/merge вне MVP.
4. Roster и часы версионируются; замена действует с указанного времени.
5. Нет нормы/входа — KPI «Не рассчитывается», не 0%.
6. Расчёт раскрывается до формулы, подстановки, единиц, событий, roster/часов, нормы и версии.
7. Основные роли: работник, бригадир, инспектор и руководитель ОТК, начальник участка, планировщик/табельщик, аналитик, администратор, аудитор.
8. Цель доступности — WCAG 2.2 AA. Выполнены автоматизированные keyboard/reflow/browser проверки на 1440 px и 390 px; ручная проверка экранным диктором ещё не заявляется выполненной.
9. Закрытие смены и готовность KPI — независимые оси. KPI: неполные данные → предварительно → ожидает независимой проверки ОТК → итог подтверждён → опубликован; закрытая смена не гарантирует final KPI.
10. Escape и false reject не смешиваются; найденный дефект не штрафует ОТК, отсутствие рекламаций не равно 100%.
11. MVP требует онлайн-подтверждение. Разрешён один pending scan с тем же UUID для retry; новые операции блокируются. Полная offline queue — после MVP или пересмотр scope до разработки.
12. Перепроизводство одной операции/модели не закрывает дефицит другой: composite использует `A_plan`, а `A_volume` остаётся диагностическим и может быть выше 100%.
13. Опубликованный маршрут неизменяем; новая версия создаётся из упорядоченного списка операций. В P0 несколько альтернатив допустимы только для полного набора сборочных рядов.
14. План и нормы изменяются безопасным `PATCH`: сервер клонирует текущую версию и заменяет только указанные ключи. Полная замена требует отдельного подтверждения.
15. Перевод сотрудника использует `transfer_from_assignment_id`: backend атомарно завершает прежнее назначение и открывает новое.
16. Rework-режим сканирования появляется только после серверной проверки открытого заказа для QR и текущей операции; номер попытки оператор не вводит.
17. Гарантированный отрицательный ответ (`REJECTED_TERMINAL`) очищает matching pending UUID и позволяет исправить QR; network/5xx/401 и `NOT_FOUND` при status lookup pending не очищают.
18. P0-Demo использует ролево-релевантное меню поверх backend capabilities: скрытый пункт не заменяет server RBAC, а доступный раздел требует одновременно подходящей роли и capability.
19. Стартовые экраны: сборка/пайка → `/scan`, QC → `/quality`, FOREMAN → `/foreman`; начальник смены/admin → сводка; планировщик → состав и часы; аудитор → расширенный экран ОТК и переделок; технолог → маршруты и новые QR.
20. Прямой запрещённый UI URL не монтирует страницу и не отправляет её запросы. Базовый `/` перенаправляет роль на стартовый экран; учётная запись без доступных разделов получает явное no-access состояние с выходом.
21. FOREMAN в P0-Demo не получает глобальные dashboard/scan/entities/configuration/workforce/quality/reports через UI: отдельный `/foreman` требует одновременно роль FOREMAN и `view_reports`; backend server-scopes ровно один ряд.
22. WORKER имеет отдельный компактный scan shell без sidebar: имя, ДЕМО и выход в topbar; смена, ряд и операция рядом с крупным QR-полем; рабочее место — в раскрываемых деталях.
23. Личный итог worker загружается только с `/me/shift-activity?limit=10`: `primary_completed` считает accepted unique COMPLETE/PRIMARY текущего actor за активную смену, rework имеет отдельный счётчик, corrected primary маркируется в истории; UI не вычисляет итог по localStorage или последним строкам.
24. Worker history показывает до 10 сохранённых COMPLETE событий с QR, рядом, операцией, временем сервера и effective status. Terminal negative ACK остаётся текущим feedback, pending до acceptance не входит в count.
25. QC имеет отдельный компактный shell без sidebar: крупный QR, «Годен»/«Брак», server DEMO-причина брака, личный checked count, reinspection отдельно и последние 10 проверок. Расширенная QualityPage остаётся у auditor/admin; FOREMAN использует только свой scoped workspace.
26. `POST /qc-inspections` атомарно сохраняет COMPLETE + QualityDecision; клиент не считает предварительный scan. Решение first-pass/reinspection определяет сервер, а переделка открывается отдельным явным действием после reject.
27. Worker и QC хранят разные canonical pending payload, но используют общую Web Lock и взаимно проверяют оба localStorage store внутри lock. В системе допускается ровно одно QR-действие; payload/actor/UUID не меняются при retry/reload/reauth.
28. QC summary полностью серверный. Corrected решение остаётся в recent с меткой «Исправлено», исключается из effective count и rework candidates; время истории — server decision `created_at`.
29. Причина брака отображается как `defect_label`, затем как сохранённый `defect_code`, и только при отсутствии обоих как «Причина не указана». Legacy-коды не переименовываются и не очищаются.
30. FOREMAN workspace имеет четыре блока: roster своего ряда, effective primary/rework за смену, последние durable проблемы сканирования и row-attributed rework. Assignment status не является online presence; альтернативный rework без row evidence не показывается.
31. Local worker/QC pending текущего браузера показывается внутри блока проблем отдельно от server history. Экран не утверждает видимость других устройств; valid pending не отменяется, generic corruption recovery сохраняет существующую аудируемую причину.
32. Портфолио-видео записывается только как реальный browser flow с ожиданием server acknowledgement. Принятый артефакт сохраняется лишь после полного сценария; failed rerun не перезаписывает его. Финальный FOREMAN-эпизод ряда 1 отделён от WIP, обработанного на сборке 2.
33. Recovery status lookup worker/QC не запускается для UUID активного POST в той же вкладке: `activeSubmissionIdRef` устраняет гонку `POST ↔ GET NOT_FOUND`, не меняя durable pending, reload/status/retry и межвкладочную семантику. Усиленные lost-response tests требуют 0 status GET до завершения POST и успешное восстановление того же UUID после reload.

## Реализованный frontend

- React 19 + TypeScript + Vite, русский интерфейс, локальные/system fonts и npm-иконки без CDN.
- Ролевой вход; сводка с пятью рядами и раздельными row metrics; worker scan HID+Enter; атомарное рабочее место ОТК; scoped workspace бригадира; общий durable pending-инвариант; генеалогия; состав/часы; ОТК/rework; plan/norm PATCH; маршруты/новые QR; отчёт, snapshot, CSV и аудит.
- API proxy: `/api` → `http://127.0.0.1:8010`; интерфейс: `http://127.0.0.1:5173`.
- Фактические проверки 25.10.2026: typecheck PASS, production build PASS, npm audit 0 vulnerabilities, live Playwright 16 PASS / 12 intentional project/viewport skips / 0 failed; после pending race-fix isolated full E2E на 5174→8011 и fresh DB также 16 PASS / 12 intentional skips / 0 failed; backend owner сообщил 76/76 PASS.
- Playwright реально проверил worker terminal bad QR/count/reload/duplicate/rework/lost reply; QC atomic accept/reject, обязательную причину, checked/reinspection, reload/history, terminal bad QR, lost reply same UUID, общий pending в обе стороны, role landing; FOREMAN own-row scope, roster/counts/problems/reworks, отсутствие данных чужих рядов и desktop/mobile reflow. Живое пользовательское исследование и реальный HID-сканер не заявляются.
- Portfolio recorder реально прошёл живую цепочку WIP → пайка → сборка 2 → брак ОТК → отдельная переделка → REWORK → повторный контроль → отчёт → scoped FOREMAN. Получен WebM/VP9 1440×900 длительностью 249,72 с; просмотрены семь ключевых кадров. Смена целиком не утверждалась.

## Инфографика

- Название: «КПД производства квадрокоптеров».
- Актуальный поток: `5 рядов (3 сборки + пайка + ОТК) → QR-скан → проверка маршрута/дублей → расчёт → отчёт`.
- Рабочее направление Infographic Artist: `system / Champ vivant gouverné` — модульная управляемая система.
- Формат: 2048×1152 px, 16:9, русский, минимум текста, ясная геометрия, без случайных логотипов.
- Рендер будущего MVP создан и сохранён в `docs/assets/kpd-production-quadcopters.png`; фактический размер 1672×941 px. WIP QR показан как предлагаемое решение для согласования, QR-мотивы иллюстративны. Направления Infographic Artist были промптами, изображение создано отдельным нативным imagegen.
- Нельзя заявлять о пользовательском тестировании или внедрении без фактических доказательств.

## QA-фокус

- Идемпотентность единственного pending QR-действия worker/QC и блокировка обоих рабочих экранов до серверного подтверждения.
- Версии маршрута, roster, часов, норм и расчёта.
- Различение дубля, допустимого повтора и переделки.
- RBAC на UI, API, прямых ссылках и экспорте.
- Историческая воспроизводимость отчёта.
- Клавиатура, диктор, фокус, ошибки, reflow и табличные альтернативы.

## Открытые вопросы

1. Оборудование и пригодность сети для online-only MVP; иначе scope пересматривается до разработки.
2. Состав и безопасность QR.
3. Точный маршрут, serial attach/detach/replace и ветви scrap/rework; партийные split/merge отложены.
4. Точные нормы `s_i`, базы позиций и применимость компонентов по участкам в рамках согласованной формулы.
5. Источник roster/часов и правила смен/перерывов.
6. Полномочия подтверждения и правила исключений.
7. Политика пересчёта истории.
8. Нужно ли позже экспортировать инфографику ровно в 2048×1152 без масштабирования нативного файла.
